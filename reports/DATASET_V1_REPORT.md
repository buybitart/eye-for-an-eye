LAB provides ground truth. PCAP provides packet realism. SHADOW provides observation without
ground truth. They are used together and never treated as equivalent.

## Feature schema

One implementation, shared with production: `eye_for_an_eye.decision.features`. Every row from
every source is built by the same parser, the same correlation engine and the same
`FeatureTransformer` the sensor runs. There is no training-only feature extractor.

| field | value |
|---|---|
| feature schema version | 1 |
| dataset schema version | 1 |
| model feature list version | 1 |
| tensor contract | `features` float32 [1, 36], fixed order |
| model features | 34 of 36 |
| excluded from the model | `previous_risk`, `available_previous_risk` |
| never model input | 46 named columns, each with a reason |
| windows | 10 s, 60 s, 900 s, from the production correlation configuration |
| missing values | explicit availability mask; unknown is never an observed zero |

The ordered list and every exclusion reason are in `datasets/model_features_v1.json`.

### SHADOW

317 rows over 14 pseudonymous sources, all UNLABELED, none in any
supervised split. this pool is a synthetic stand-in. It exercises the shadow path and gives a distribution to compare against; it is not evidence about real traffic.

| property | value |
|---|---|
| sensor placement | synthetic stand-in for a sensor placed in front of a small service estate; no real deployment has produced telemetry for this project yet |
| label | unlabeled / shadow_observation |
| pseudonymisation | fixed salt, because this pool contains no real address; a real export uses HMAC under a local secret that is never committed |
| redaction | default deny: an allowlist of bounded numbers, flags and short enumerations |
| never exported | payload, headers, credentials, cookies, tokens, authorization, command text, keyed payload digests, source address |
| kept for analysis only | math_score, model_score, ml_score, risk, action, would_enforce, disagreement, confidence |
| collection bounds | max 5000 samples, max 33554432 bytes, truncated: False |
| raw retention | 30 days |

The mathematical score, the model score, the fused risk and the action are kept beside each row
so a reviewer can see what the system thought. None of them is a label and none is a feature:
`schema.NEVER_MODEL_INPUT` names each one with the reason.

## Known limitations

- Every source is synthetic. LAB and PCAP are generated here; the shadow pool is a stand-in for
  telemetry no deployment has produced yet. Nothing in this dataset is evidence about real traffic.
- Reviewed shadow rows: **0**. Nobody has reviewed anything, so the highest-realism source
  contributes distribution and review candidates, not labels.
- PCAP realism is packet-level, not population-level: varied TTL, TCP options, window sizes,
  segmentation, retransmission, reordering and one IPv6 capture, but still one lab topology.
- Live loopback runs are few and short (95 events), because
  real time cannot be compressed. They validate the event schema rather than carry the corpus.
- 9 availability masks never vary, so a model fitted here learns nothing
  about missing counts or missing timing.
- Rows from one group are correlated windows; the effective sample size is
  182 groups, not 2334 rows.
- Class balance is a generator artefact. A real sensor is heavily imbalanced.
- The dataset cannot express authorisation: an authorised scan and an unauthorised one look
  identical to a behavioural sensor. That belongs to the policy allowlist, not a model.

## Recommended improvements before Logistic Regression

1. Nothing blocks the baseline. Train it on the frozen split, report per-source metrics, and do
   not re-tune against the test set.
2. Report metrics separately for LAB and PCAP rows. If they diverge sharply, the model has learned
   the generator rather than the behaviour.
3. Widen the LAB generator using the shadow distribution - more destinations per source, slower
   inter-arrival - without ever using a shadow decision as a label.
4. Review the 61 out-of-distribution
   shadow rows and add the behaviours they show as dataset-v2 scenarios.
5. Add a second, independent scanning tool so positive behaviour is not all from one generator
   family.
